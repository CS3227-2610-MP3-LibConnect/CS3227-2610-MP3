# Member Borrow Implementation Tasks

This checklist follows [`design.md`](./design.md). Implement tasks in order; the design is the approved behavior and API-contract source. Editable application TypeScript sources are under `apps/api/src`, `apps/client/src`, and `packages/shared/src`; `dist` is generated build output.

## Implementation checklist

- [x] **Implement member borrow capacity and copy eligibility operations** - Add server-side operations for the authenticated member's active-loan count/remaining slots and for checking a copy ID before staging. Use the active actor rather than client identity, require member access, return book/copy details for an available copy, and do not mutate loan or copy state during staging.
  - Acceptance criteria: The capacity response reflects the authenticated member's `ACTIVE` loans and the 10-loan limit; unknown copy IDs use the established API error envelope; only `AVAILABLE` copies can be staged; successful eligibility checks return the book and copy data needed for a card; calls create no loans, change no copy status, and reserve no copy; librarian, signed-out, and inactive accounts cannot use member operations.
  - References: Design §§ Product specifications, Acceptance criteria 1–5, Technical specifications, Integration specifications; `apps/api/src/http/auth.ts`; `apps/api/src/routes/catalog.ts`; `apps/api/src/storage/repositories.ts`; `packages/shared/src/domain/records.ts`.

- [x] **Implement per-copy member loan confirmation with a concurrency-safe limit** - Add the member confirmation workflow that rechecks the authenticated member, every submitted copy, and the current active-loan limit. Process eligible copies independently so one unavailable copy does not prevent other eligible copies from being borrowed. Keep each successful loan creation and its copy transition consistent, and return a success or failure reason for every submitted copy.
  - Acceptance criteria: Each successful result corresponds to a valid `LoanRecordSchema` record attributed to the authenticated member and a copy changed from `AVAILABLE` to `ON_LOAN`; unavailable or missing copies fail individually while other eligible copies succeed; the response includes a per-copy result and reason for failures; no member can exceed 10 active loans under concurrent or repeated confirmations; the server ignores client-supplied member identity; each loan uses server-generated ID/timestamps and a due date 30 days after borrowing; this member operation does not allow `RESERVED` copies or alter librarian loan creation behavior.
  - References: Design §§ Product specifications, Acceptance criteria 7–12, Technical specifications, Integration specifications, Risks and tradeoffs; `apps/api/src/storage/workflows.ts`; `apps/api/src/storage/repositories.ts`; `packages/shared/src/domain/records.ts`; `Overview.md`.

- [x] **Expose the member borrow API and wire the workflow into the server** - Add the authenticated member routes for capacity lookup, add-copy eligibility, and confirmation. Validate request bodies with strict schemas, use the proposed paths and payloads in the design, map service outcomes to the shared response/error conventions, and connect the routes to the server's storage/workflow instances.
  - Acceptance criteria: `GET /api/v1/member/borrow-capacity` returns active-loan count and remaining slots; `POST /api/v1/member/borrow-items` accepts `{ copyId }` and has no persistence side effect; `POST /api/v1/member/loans` accepts `{ copyIds }` and returns one outcome for each submitted ID; malformed or unknown fields produce the established validation error envelope; authentication and member-role checks are server-side; the API is mounted without changing existing catalog or librarian route behavior.
  - References: Design §§ Technical specifications and Integration specifications; `apps/api/src/server.ts`; `apps/api/src/routes/catalog.ts`; `apps/api/src/http/errors.ts`; `apps/api/src/storage/workflows.ts`.

- [x] **Add the member borrow page and capacity-aware staging flow** - Add a protected member route and a Borrow button in the member navigation bar that opens it. Load the server-reported remaining capacity, allow copy ID entry and an explicit Add copy action, display eligible copies as cards, prevent duplicate cards and staging beyond remaining slots, and allow staged copies to be removed. Keep staged state in the client and ensure it never changes backend loan or copy state.
  - Acceptance criteria: Only members can render the page; the member navigation bar shows a Borrow button that opens the page; capacity is obtained through the credentialed client API; Add copy submits the ID to the backend and displays a card only after eligibility succeeds; unknown or unavailable IDs display an error and add no card; repeated IDs are not added twice; the Add action is disabled or rejected when staged count reaches remaining capacity; removing a card restores one staging slot; no loan or copy status changes before confirmation; existing member catalog/detail navigation and librarian dashboard behavior remain intact.
  - References: Design §§ Product specifications, Acceptance criteria 1–7, Technical specifications, Integration specifications; `apps/client/src/App.tsx`; `apps/client/src/api/base.ts`; `apps/client/src/components/MemberNavigation.tsx`; `apps/client/src/pages/MemberBookDetail.tsx`; `apps/client/src/auth/ProtectedRoute.tsx`.

- [x] **Add confirmation and per-copy outcome UI** - Show a confirmation dialog listing staged books, provide confirm and cancel actions, submit only staged copy IDs after confirmation, and render successes and failures from the server response. Treat confirmation results as authoritative because availability and loan capacity may have changed since staging.
  - Acceptance criteria: The dialog lists all staged books; cancel creates no loans and changes no copy statuses; confirmation calls the member loan endpoint; successful and failed copies are clearly distinguished, with failure reasons; if one copy became unavailable, other eligible copies can still be borrowed; server-reported limit failures are communicated; staged items are not described as reserved or borrowed before successful confirmation.
  - References: Design §§ Product specifications, Acceptance criteria 6–12, Integration specifications, Risks and tradeoffs; `apps/client/src` member pages and API modules.

- [x] **Verify the member borrow acceptance criteria** - Add focused client and API coverage for staging, confirmation, ownership, per-copy partial success, and the 10-loan limit, then run the project build/test checks and authenticated Firestore Emulator verification.
  - Acceptance criteria: Automated coverage verifies member-only access, unknown/unavailable copy errors, capacity-based staging limit, duplicate prevention, no state change before confirmation/cancel, successful loan and copy updates, partial success when one copy becomes unavailable, per-copy failure reasons, ownership isolation, and concurrent/repeated requests never exceeding 10 active loans; `npm run build` and `npm test` pass; Firestore-backed checks use the configured emulator and not production credentials; any manual UI verification limitations are recorded.
  - References: Design §§ Acceptance criteria 1–12, Technical specifications, Risks and tradeoffs; `package.json`; `tests/active-actor.test.mjs`; `tests/client-member-detail.test.mjs`; `firebase.json`; `firestore.rules`.

## Repository conventions and dependencies

- React Router pages and role-protected routes are registered in `apps/client/src/App.tsx`; `ProtectedRoute` checks the restored session and account type (`apps/client/src/auth/ProtectedRoute.tsx`, `apps/client/src/auth/AuthContext.tsx`).
- Client requests use `apiRequest`, which sends cookies and uses the `/api/v1` prefix (`apps/client/src/api/base.ts`).
- API request validation uses Zod and `parseRequest`; errors use the shared `{ error: { code, message, fields? } }` envelope (`apps/api/src/routes/catalog.ts`, `apps/api/src/http/errors.ts`).
- Business API requests pass through active-actor middleware in `apps/api/src/server.ts`; role checks must still be applied to member-specific operations (`apps/api/src/http/auth.ts`).
- Firestore reads and writes belong in server-side storage/workflow code. Loan and copy shapes are represented by `LoanRecordSchema` and `BookCopyRecordSchema` (`apps/api/src/storage/workflows.ts`, `apps/api/src/storage/repositories.ts`, `packages/shared/src/domain/records.ts`).
- The existing `LibraryWorkflows.createLoan` is librarian-only and handles one copy, so implement the member operation separately and preserve librarian behavior (`apps/api/src/storage/workflows.ts`).
- Tests use Node's built-in test runner; `npm test` builds before running the listed tests. Firestore-backed verification scripts use the configured Firebase Emulator (`package.json`, `tests/`, `firebase.json`).
- Current member pages are under `apps/client/src/pages/`, and member navigation is in `apps/client/src/components/MemberNavigation.tsx`.
