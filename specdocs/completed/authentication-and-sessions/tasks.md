  - Acceptance criteria: The client starts on the configured port, its build succeeds, and the development configuration can call the API at `http://localhost:3000` with cookies enabled.

- [x] **Configure credentialed API requests and Origin checks** - Configure Express CORS for the exact `CLIENT_ORIGIN` and credentialed requests. Add middleware that rejects state-changing requests whose `Origin` does not match the configured origin. Keep health checks public and do not add rate limiting.
  - Acceptance criteria: Requests from the configured client origin can send and receive the session cookie; a mismatched origin is rejected for state-changing requests; health checks remain accessible without a session; no rate-limit middleware is introduced.
  - References: Design sections “Browser and request security,” “API enforcement,” and “Resolved decisions”; `apps/api/src/server.ts`; `.env` (`CLIENT_ORIGIN`).

- [x] **Expose registration, login, logout, and session routes** - Add auth routes under `/api/v1/auth` and connect them to `AccountStorage`. Validate inputs with Zod. Registration accepts the selected account type and required fields, creates no session, and leaves librarians inactive. Login requires the selected `MEMBER` or `LIBRARIAN` type, authenticates against stored credentials/status, regenerates the session ID, and returns a safe account summary. Return a distinct account-disabled error for valid credentials belonging to an inactive member; keep invalid credentials and inactive librarian feedback generic. For native HTML login forms, redirect inactive members to `/login-disabled.html`. Logout destroys the session. Session status returns the approved signed-in or signed-out response.
  - Acceptance criteria: Registration and login work without an existing session; a member is active after registration but must log in separately; a librarian remains inactive and cannot log in before activation; invalid email/password/type combinations and inactive librarian accounts use a generic credential error; valid credentials for an inactive member produce a distinct disabled-account response; login establishes a regenerated session; logout invalidates it; `GET /api/v1/auth/session` returns `200` with `{ authenticated: false }` when signed out and `{ authenticated: true, user: <safe account summary> }` when signed in; no response includes a password hash or session identifier.
  - References: Design sections “Product specifications,” “Acceptance criteria,” “Proposed API surface,” “Session and authorization flow,” and “Resolved decisions”; `apps/api/src/storage/accounts.ts`; `apps/api/src/http/errors.ts`; `packages/shared/src/domain/records.ts`.

- [x] **Enforce active-account access across business APIs** - Apply the active-actor policy consistently to all business API routes, leaving only the approved public endpoints exempt. Ensure role checks use the server-loaded actor and account deactivation removes that user’s persisted sessions.
  - Acceptance criteria: Unauthenticated or expired-session business requests receive `401`; inactive accounts cannot use business APIs; role or manager values supplied by the client do not grant access; health and auth entry points remain public; deactivating an account invalidates its active sessions and subsequent requests are denied.
  - References: Design sections “Acceptance criteria,” “API enforcement,” and “Integration specifications”; `apps/api/src/http/auth.ts`; `apps/api/src/server.ts`; `apps/api/src/storage/accounts.ts`; `apps/api/src/storage/firestore-session-store.ts`.

- [x] **Implement client auth pages and route protection** - Add registration and login forms, a session-aware auth state, protected-page handling, and logout. Display the disabled-account message when login returns the distinct inactive-member response.
  - Acceptance criteria: Signed-out users are redirected to sign-in before protected pages render; session restore displays the signed-in state after reload; login sends the selected account type; valid credentials for an inactive member display the account-disabled message; invalid credentials and inactive librarian accounts retain generic feedback; successful registration directs the user to sign in rather than treating them as authenticated; logout clears the signed-in UI and session; API `401` responses return the user to sign-in; browser requests include credentials.

  - Acceptance criteria: Static registration and login forms contain no scripts and submit natively; registration success redirects directly to `/login.html` and does not create a session; login success establishes a session and redirects to the application root; valid credentials for an inactive member redirect to `/login-disabled.html`, while inactive librarian accounts and invalid credentials retain generic credential feedback; redirects stay on the configured `CLIENT_ORIGIN`; JSON clients retain existing response contracts.

  - Acceptance criteria: Every design acceptance criterion has a corresponding automated check or documented manual verification step; the emulator check confirms successful native registration redirects directly to `/login.html` without a session; checks distinguish valid credentials for an inactive member from invalid credentials in both login flows and confirm inactive librarians retain generic feedback; verification uses the Firestore Emulator rather than production credentials; local instructions use the configured client port/origin and API port; no secrets, passwords, or session identifiers are exposed in logs or verification output.
  - References: Design “Acceptance criteria,” “Risks and tradeoffs,” and “Resolved decisions”; `PLAN.md` testing strategy and development environment separation; `firebase.json`; `apps/api/src/server.ts`.

## Repository conventions and dependencies

- The API is Express with TypeScript and mounts routes under `/api/v1`; request parsing and validation use Zod (`apps/api/src/server.ts`, `apps/api/src/routes/catalog.ts`).
- API errors use `{ error: { code, message, fields? } }` (`apps/api/src/http/errors.ts`).
- Account operations use Firestore repositories and Argon2id hashing (`apps/api/src/storage/accounts.ts`, `apps/api/src/storage/repositories.ts`).
- Sessions use `express-session` with a Firestore-backed store and `httpOnly`, `sameSite: 'lax'` cookies (`apps/api/src/server.ts`, `apps/api/src/storage/firestore-session-store.ts`).
- The catalog client sends cookies with `credentials: 'include'` (`apps/client/src/api/catalog.ts`). The client application itself does not yet exist; this plan adds the Vite + React + TypeScript scaffold as confirmed in the design amendment.
- Local API and Firestore Emulator configuration are already present (`.env`, `firebase.json`). Production origins and credentials must be supplied separately at deployment.
